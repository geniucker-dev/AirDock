# 10-bit and HDR playback

The receiver displays 8-bit NV12/YUV420P/YUVJ420P and little-endian 10-bit P010 /
YUV420P10. PQ (ST 2084) and HLG (BT.2100) HDR content is mapped to the existing
SDR Iced window. This enables HDR content playback on ordinary SDR monitors and
on Windows HDR desktops using the application's SDR surface. It does not create
a native HDR swapchain, negotiate monitor HDR metadata or promise HDR luminance
at the screen. Diagnostics label `PQ HDR → SDR` / `HLG HDR → SDR` explicitly.

## GPU and colour path

10-bit planes upload directly to reusable R16Uint / RG16Uint textures. The shader
extracts the high ten bits of P010 or low ten bits of YUV420P10 before bilinear
sampling. Unused bits are masked. Positive/padded and negative strides and odd
chroma dimensions are validated as for 8-bit input. No CPU YUV-to-RGBA conversion,
software pixel downconversion or optional GPU normalized-16 texture feature is
required. The existing 8-bit filtering path remains separate.

Limited-range 10-bit luma uses 64–940; chroma centres on 512 with a nominal span
of 896. Full range uses 0–1023. YUV conversion retains the existing supported
matrices. HDR with missing matrix/primaries uses BT.2020 NCL / BT.2020, unless
BT.709 is explicitly signalled; missing HDR range defaults to limited. Existing
unspecified SDR range/matrix behaviour is preserved. Explicit BT.2020 or Display
P3 SDR primaries are also converted in linear light.

PQ decoding uses ST 2084 absolute luminance. Peak selection uses valid MaxCLL,
then mastering-display maximum luminance, then a stable 1000-nit fallback.
Malformed/truncated/invalid metadata is ignored; the supported peak is 100–10000
nits. HLG uses the BT.2100 nominal 1000-nit display and system gamma 1.2 OOTF.

A zero-black BT.2390 Hermite shoulder maps source luminance into a 100-nit SDR
reference. Linear D65 BT.2020 / Display P3 transforms produce BT.709 RGB; chroma
compression toward the neutral axis keeps out-of-gamut highlights in range while
preserving luminance and hue direction. The SDR signal is encoded once, respecting
whether the actual render target performs sRGB encoding itself.

Transfer and tone curves use one 32 KiB, 4096×2 R32Float LUT. Tables are generated
and uploaded only on metadata changes, with the ordinary SDR path bypassing LUT
and tone operations. Integer pipelines, planes, bindings and tables are cached.
Scheduler intake measures actual backing allocations, including word formats and
stride padding, and stops receiving when its frame/nominal byte budget is reached.
Future/paused frames retain backpressure; shutdown releases blocked producers.
HDR still increases input bandwidth and shader work; no hardware performance
parity claim follows from this implementation or software-renderer tests.

## Verification and bounds

The production shader oracle retains 18,816 original SDR comparisons and adds
96,800 comparisons across byte/word input, both ranges, linear/sRGB targets,
PQ/HLG, BT.709/BT.2020/P3 primaries, 400/1000/4000/10000-nit peaks, junk unused
sample bits, wide-gamut SDR and repeated format/metadata switching. Its reference
derives primary matrices independently from chromaticity coordinates, evaluates
transfer equations in f64 and expresses the shoulder as a cubic Bezier. Local
Vulkan llvmpipe maximum error is 1/255; Windows results are in the final CI report.

Actual HEVC Main10 fixtures validate SDR/PQ/HLG decoding, static metadata survival,
encrypted mirroring transitions back to 8-bit SDR, and PQ/HLG fMP4 HLS playback.
Synthetic fixtures are generated by external tools, never by the receiver.

Native Windows HDR output, Dolby Vision reconstruction/dynamic metadata and
HDR10+ dynamic scene mapping are not implemented. Compatible PQ/HLG base video
can be displayed with the static policy above, but dynamic HDR correctness is not
claimed. BT.2020 CL, unsupported primaries, big-endian/12-bit and non-420 formats
remain explicit errors. Real iPhone HDR interoperability, hardware decode output,
display appearance/calibration and sustained GPU performance require physical
Windows/iPhone acceptance; these are not passed by software GPU or null audio CI.
